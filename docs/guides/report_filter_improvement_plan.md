# 案件搜尋與篩選改善方案

## 1. 目的

改善案件看板的關鍵字搜尋、狀態篩選、案件類型篩選與標籤篩選，讓篩選條件的畫面狀態、實際查詢條件與案件結果保持一致，並降低查詢錯誤與快速操作造成的資料覆蓋問題。

目前「已完成案件看不到」的個案，確認是因為狀態篩選選取了「待辦」，不是系統查詢錯誤。但現有介面仍有機會讓「狀態篩選」與「隱藏已完成」形成互相矛盾的條件，因此本方案一併納入改善。

## 2. 現況流程

1. `ReportSearchInput.vue` 將輸入內容 debounce 300 毫秒後寫入共用的 `keyword`。
2. `DashboardView.vue` 監聽關鍵字、排序、隱藏公告與隱藏已完成，變更後自動呼叫 `fetchReports`。
3. `ReportFilterPanel.vue` 的狀態、案件類型與標籤先修改共用 filter state，按下「套用篩選」後才呼叫查詢。
4. `reports.ts` 將條件轉換為 Supabase query：
   - `status`
   - `template_type`
   - `report_tags.tags.name`
   - `subject` 或 `remarks` 關鍵字
5. 狀態、案件類型、標籤、排序及隱藏設定會保存於 `localStorage`；關鍵字目前不保存。

## 3. 待改善項目

### 3.1 狀態條件與隱藏已完成條件可能互相矛盾

當使用者選取「已完成」，同時「隱藏已完成」仍為啟用，查詢會同時產生：

```text
status IN ('completed')
status != 'completed'
```

結果必定為空，容易被誤認為已完成案件不存在。

**建議：**

- 選取明確狀態時，讓明確狀態優先，暫時忽略 `hideCompleted`；或
- 使用者選取「已完成」時自動關閉「隱藏已完成」；並在介面提供明確提示。

建議採用第一種方式，因為查詢結果應優先遵循使用者明確選取的狀態。

### 3.2 「清除全部」後列表不一定立即重新查詢

`DashboardView.vue` 目前沒有監聽 `selectedStatuses`、`selectedTemplateTypes`、`selectedTags`。因此當使用者只修改這三類條件，再按「清除全部」時，filter state 雖已清空，列表可能仍顯示前一次查詢結果。

**建議：**

- 將所有篩選欄位納入查詢觸發機制；或
- 由 `clearFilters()` 直接發出清除事件，讓 Dashboard 立即重新查詢。

建議都做，同時保留「套用篩選」按鈕，避免每次點擊條件都立即發出請求。

### 3.3 關鍵字搜尋範圍與畫面提示不完全一致

目前搜尋只查詢 `subject` 與 `remarks`，不包含：

- `formatted_content`
- `report_items.content`
- `department`
- 標籤名稱

**建議：**

- 短期：將輸入框提示改為「搜尋案由或內部備註」，使文字與實際行為一致。
- 中期：若需求是全文搜尋，新增後端查詢策略或資料庫 view，統一搜尋案件主表、項目內容與標籤。

不建議直接在前端載入全部資料後搜尋，避免資料量增加後造成效能與權限問題。

### 3.4 Supabase 關鍵字查詢需要安全處理特殊字元

目前查詢字串直接插入使用者輸入。逗號、括號、百分比符號或 PostgREST 特殊字元可能造成查詢格式錯誤或結果不符合預期。

**建議：**

- 建立集中式查詢字串 escape helper。
- 為逗號、括號、百分比及底線等特殊字元補測試。
- 若後端資料庫支援，優先改用 RPC 或全文搜尋函式，避免在前端組合複雜 `.or()` 字串。

### 3.5 快速搜尋可能發生回應順序覆蓋

關鍵字雖然有 300 毫秒 debounce，但不同查詢仍可能同時進行。若較早的請求較晚完成，可能以舊結果覆蓋較新的搜尋結果。

**建議：**

- 在 store 增加 request sequence 或 AbortController。
- 只有最新請求可以更新 `reports` 與 `loading` 狀態。
- 查詢錯誤也應與目前請求的 sequence 綁定，避免舊錯誤覆蓋新結果。

### 3.6 標籤選項來源會隨目前結果集縮小

`allUniqueTags` 與 `topTags` 是從目前已載入的 `reports` 計算而來。當使用者先套用案件類型或狀態篩選後，標籤選項也會跟著縮小，可能無法再選取其他案件中的標籤。

**建議：**

- 短期：標籤選項由未套用標籤條件的基礎資料集計算。
- 中期：新增 `fetchAvailableTags()`，由資料庫取得目前使用者可見的完整標籤清單與使用次數。
- 已選標籤即使不在目前候選清單，也必須繼續顯示並可取消。

### 3.7 持久化篩選條件需要更清楚的使用者提示

篩選條件會保存在 `localStorage`，重新整理或重新進入看板後仍會套用。這可能讓使用者忘記先前的狀態篩選，例如目前選到「待辦」而誤以為「已完成」案件不存在。

**建議：**

- 在看板顯示目前已套用的條件摘要。
- 顯示「已完成案件已隱藏」等明確提示。
- 提供「重設篩選」按鈕，且重設後立即重新查詢。
- 評估是否需要保存篩選條件；若保留，應在頁面首次載入時明確顯示已恢復條件。

## 4. 建議實作順序

| 優先級 | 項目 | 目標 |
| :--- | :--- | :--- |
| P0 | 解決狀態與隱藏已完成的矛盾 | 選取已完成時不再被隱藏條件抵銷 |
| P0 | 修正清除全部後立即重新查詢 | 畫面結果與 filter state 同步 |
| P1 | 統一關鍵字查詢 escape 與 request sequence | 降低查詢錯誤與舊結果覆蓋 |
| P1 | 調整搜尋提示文字 | 讓 UI 說明符合實際查詢欄位 |
| P2 | 改善標籤候選來源 | 避免篩選後標籤選項消失 |
| P2 | 增加篩選條件摘要與持久化提示 | 降低使用者誤判 |
| P3 | 評估案件全文搜尋 | 擴大搜尋範圍並維持可接受效能 |

## 5. 測試規劃

### 單元測試

- `status = completed` 且 `hideCompleted = true` 時，確認採用明確狀態優先策略。
- 未選狀態時，確認預設仍排除 `archived` 與 `deleted`。
- `clearFilters()` 後所有 filter state 都恢復預設值。
- 清除狀態、案件類型或標籤後會觸發重新查詢。
- 關鍵字特殊字元會被正確 escape。
- 同時發出多個查詢時，只有最新查詢可以更新結果。

### 元件測試

- 選取「已完成」後，畫面顯示正確的已完成案件。
- 「隱藏已完成」啟用時，畫面顯示明確狀態提示。
- 點擊「清除全部」後，條件按鈕與案件列表同步更新。
- 標籤搜尋只過濾標籤按鈕，不會誤觸發案件 API 查詢。

### 驗收條件

1. 使用者選取「已完成」後，可以看到所有符合其他條件的已完成案件。
2. 使用者清除全部條件後，列表立即回到預設案件集合。
3. 搜尋輸入特殊字元不會造成查詢錯誤。
4. 快速連續輸入關鍵字後，列表只顯示最後一次搜尋結果。
5. 重新整理後，若篩選條件被恢復，畫面會明確告知目前套用的條件。

## 6. 非本次範圍

- 不改變案件狀態的業務定義。
- 不新增提醒規則或背景通知功能。
- 不在前端複製完整案件資料進行全文搜尋。
- 不改變現有任務清單的獨立查詢流程。

## 7. 執行進度

### 已完成

- 選取「已完成」時自動關閉「隱藏已完成」，並顯示篩選提示。
- 頁面載入時若恢復了互相矛盾的已完成篩選狀態，會自動關閉「隱藏已完成」。
- 「清除全部」增加重設版本號，Dashboard 會立即重新查詢，且不會讓每次點選條件都立即查詢。
- 關鍵字輸入提示調整為「搜尋案由或內部備註」。
- 關鍵字查詢新增特殊字元 escape，並補上測試。
- Reports store 增加 request sequence，只有最新查詢可以更新案件結果與 loading 狀態。

### 尚未執行

- 看板顯示完整篩選條件摘要與持久化狀態提示。
- 案件全文搜尋與 `report_items`、標籤內容整合。
